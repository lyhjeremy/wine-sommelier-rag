Wine Sommelier RAG
Every recommendation cited to a review

Retrieval-augmented generation over Wine Enthusiast reviews

Ask for a wine in plain English and get bottles from 30,000 indexed reviews

A request such as "a bold red under $25 for a steak dinner" goes through dense and BM25 retrieval and a cross-encoder reranker, then to Claude, which may recommend only the reviews it was handed and cites each with [n]. On a 12-query benchmark the reranker lifted nDCG@10 from 0.69 to 0.83. BM25 fusion on its own made ranking worse: MRR fell from 0.88 to 0.76.

The measurement

Three retrievers, twelve queries

src/eval.py runs three setups over twelve requests, from "a crisp, mineral white to go with fresh oysters" to "an affordable Argentine Malbec under $20". Each request has a written rubric (wine family or grape, country, price cap, descriptor words), and a review counts as relevant if it meets the rubric. Pick a metric to follow it through the pipeline.

Recall@10 is low for every system because most rubrics match hundreds of reviews, and ten results can hold only ten of them. The ranking metrics are the ones that separate the systems.

What the table says

BM25 fusion alone made ranking worse

Fusing a BM25 keyword index into the dense ranking left precision about where it was and dropped MRR from 0.88 to 0.76: the first relevant wine landed lower. BM25 pulls in reviews that share words with the request but describe the wrong kind of wine, and Reciprocal Rank Fusion rewards any review that shows up in both lists, even far down them: a review ranked 61st in both outscores the one dense search put first. The calculator uses the fusion formula from src/hybrid.py (k = 60, 80 candidates from each list in the benchmark).

The cross-encoder (ms-marco-MiniLM-L-6-v2) fixes this by reading the request and each review together and re-scoring the top 80 fused candidates. With it, precision rose to 0.82 and nDCG@10 to 0.83, both about 21% above the dense baseline. The BM25 row stays in the table because it is a result too.

The grounding

It cannot recommend a bottle it did not retrieve

The system prompt tells Claude to recommend only from the retrieved reviews, to cite each pick by its [n] index, and to say so if none of them fit. Price, country, grape and minimum score go into the vector query as metadata filters, so a $25 cap never spends a retrieval slot on an $80 bottle. The answer prints with the reviews it cites underneath.

Limitations

Twelve queries, scored by rules

The benchmark is small, and relevance comes from keyword-and-metadata rules, with no human judges. A rule that rewards grape and price will favor retrievers that match on grape and price. The rules are in src/eval.py where anyone can read them, and the comparison is fair between systems, but the absolute numbers would need a hand-labeled set to mean more. Only the averages are saved, so per-query results can't be shown here.

The default index holds the 30,000 highest-scored reviews (--limit 30000), not all 129,971; --all indexes everything. The reviews come from one magazine and carry its coverage gaps. Constraints such as price are set with CLI flags; the system does not yet read "under twenty bucks" out of the sentence.

How it was built

Stack

Corpus
The winemag-data-130k-v2 Wine Enthusiast dataset, de-duplicated; 30,000 reviews indexed by default
Embeddings
all-MiniLM-L6-v2 (384 dimensions) via sentence-transformers, on Apple MPS, CUDA or CPU
Vector store
Chroma, cosine similarity, persisted to disk
Sparse retrieval
BM25 (rank-bm25), fused with Reciprocal Rank Fusion, k = 60
Reranking
Cross-encoder ms-marco-MiniLM-L-6-v2 over the fused shortlist (60 candidates by default, 80 in the benchmark)
Generation
Claude through the Claude CLI by default; ANTHROPIC_API_KEY switches to the API
Evaluation
python -m src.eval: P@10, Recall@10, MRR, nDCG@10 on 12 rubric-labeled queries
